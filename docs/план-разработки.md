# План разработки проекта

## Исходная цель
Автоматизация информирования потенциальных клиентов о новых судебных делах (КАД kad.arbitr.ru), поиск совпадений по базе контактов и отправка коммерческих предложений.

---

## Текущий статус и дорожная карта

```
[ГОТОВО: Этап 1]  Клиент и парсер КАД (Playwright, Xvfb, пагинация, ретраи, суды, роли участников)
        │
        ▼
[ГОТОВО: Этап 2]  База данных и модели ORM
  ├── SQLAlchemy async + asyncpg + Alembic
  ├── Модели данных: Case / Side, Contact
  └── docker-compose.yml (PostgreSQL + env) и первая миграция
        │
        ▼
[ГОТОВО: Этап 3]  Скрипт наполнения тестовыми контактами
  └── scripts/seed_contacts.py:
        • Заполнение таблицы `contacts` реалистичными тестовыми данными (включая ООО "РЕМИСТР")
        • Опция `--clean` для сброса и перезаполнения
        • Идемпотентный upsert по ИНН
        │
        ▼
[ГОТОВО: Этап 4]  Сервис рассылки (Mailer)
  ├── app/services/mailer.py:
  │     • Асинхронная отправка email по SMTP (`aiosmtplib`)
  │     • Текстовый формат: "{ФИО}, на вас подали в суд. Ссылка на дело: {ссылка}"
  │     • Поддержка SSL (порт 465) и STARTTLS (порт 587)
  └── scripts/test_email.py:
        • Скрипт отправки тестового уведомления на указанный адрес
        │
        ▼
[ГОТОВО: Этап 7]  Оркестрация FastAPI + APScheduler
  ├── Матчинг по ФИО/наименованию (нормализация ОПФ, кавычек, ё→е)
  ├── Периодический опрос КАД (AsyncIOScheduler, настраиваемый интервал)
  ├── Журнал notifications (дедупликация писем, повтор при ошибке SMTP)
  └── API: GET /health, POST /api/v1/monitor/trigger
        │
        ▼
[Этап 5: Проверка сквозного сценария]
  └── Скрипт проверки цепочки:
        • Получение дела из КАД (или тестового дела)
        • Выборка целевого контакта из БД (по совпадению ИНН/названия)
        • Отправка письма через Mailer
```

## Детализация этапов

### Этап 2: База данных и модели ORM
1. **Зависимости и конфигурация**:
   - `pyproject.toml`: добавление `sqlalchemy>=2.0`, `asyncpg`, `alembic`.
   - `app/config.py`: параметры подключения `database_url`.
   - `docker-compose.yml`: сервис PostgreSQL 16 с volume и healthcheck.
2. **Базовый модуль БД (`app/database.py`)**:
   - `create_async_engine`, фабрика сессий `async_sessionmaker`, `Base = DeclarativeBase`.
3. **Модели (`app/models/`)**:
   - `Case` (`id`, `guid`, `case_number`, `case_type`, `court`, `judge`, `start_date`, `created_at`) с уникальным индексом по `guid`.
   - `Side` (`id`, `case_id`, `role`, `name`, `inn`, `address`) со связью `ForeignKey("cases.id")`.
   - `Contact` (`id`, `company_name`, `inn`, `email`, `phone`, `is_active`, `created_at`).
4. **Миграции (Alembic)**:
   - Инициализация асинхронного `env.py`.
   - Первая миграция создания таблиц `cases`, `sides`, `contacts`.
5. **Тесты**:
   - Тесты CRUD и отношений моделей через pytest.

### Этап 3: Скрипт наполнения тестовыми контактами
1. `scripts/seed_contacts.py`:
   - Наполнение таблицы `contacts` тестовыми записями (включая компании из реальных тестовых выборок КАД, например ООО "РЕМИСТР", для сквозного тестирования).
   - Опция `--clean` для сброса и перезаполнения.

### Этап 4: Сервис рассылки (Mailer)
1. `app/services/mailer.py`:
   - Настройки SMTP в `app/config.py` (хост, порт, логин, пароль, отправитель, режим SSL/TLS).
   - Формирование HTML/plain-text сообщений с подстановкой параметров дела.
   - Асинхронная отправка через `aiosmtplib`.

### Этап 5: Сквозной сценарий
1. `scripts/e2e_pipeline.py`:
   - Запуск пайплайна: парсинг дела -> поиск ответчика среди `Contact` по ИНН -> отправка КП через `Mailer`.

### Этап 7: Оркестрация FastAPI + APScheduler (ГОТОВО)
1. **Конфигурация (`app/config.py`, `.env.example`)**:
   - `SCHEDULER_ENABLED`, `KAD_POLL_INTERVAL_MINUTES`, `KAD_POLL_COURTS`, `KAD_POLL_CASE_TYPES`, `KAD_MAX_PAGES_PER_POLL`.
   - Правило `KAD_POLL_CASE_TYPES=[]` — пустой список означает **один запрос «без фильтра»** (поле `CaseType` не передаётся, КАД возвращает все типы G/A/B сразу, как ручной поиск на сайте); непустой — отдельный запрос на каждый тип.
2. **Матчинг по имени (`app/services/matching.py`)**:
   - `normalize_name()`: нижний регистр, ё→е, удаление ОПФ (ООО/ИП/АО...), кавычек и пунктуации, схлопывание пробелов.
   - `match_side_to_contacts()`: точное совпадение нормализованных строк либо включение (≥6 символов); только активные контакты.
3. **Мониторинг (`app/services/monitor.py`)**:
   - `save_case_if_new()`: дедупликация по `guid`.
   - `run_monitoring_cycle()`: активные контакты → опрос КАД (суды/типы из настроек) → сохранение новых дел → матчинг ответчиков → email; защита от параллельного запуска (`asyncio.Lock`).
   - Журнал `notifications` (пара `case_id × contact_id` уникальна): письмо не дублируется, а ошибка отправки повторяется в следующем цикле.
4. **Планировщик (`app/scheduler.py`)**:
   - `AsyncIOScheduler` с interval-джобой `kad_periodic_monitoring`; `start_scheduler` / `stop_scheduler` / `get_scheduler_status`.
5. **API (`app/main.py`)**:
   - Lifespan: проверка БД → запуск планировщика; shutdown: остановка планировщика, закрытие сессии КАД и пула БД.
   - `GET /health` (БД + статус планировщика), `POST /api/v1/monitor/trigger` (фоновый запуск цикла, 202).
6. **Сводка о новых делах (`app/services/summary.py`)**:
   - В конце цикла все новые дела (дедуп по `guid`) дописываются в дневной файл `data/reports/kad_YYYY-MM-DD.md` (append — история за день накапливается).
   - При заданном `SUMMARY_EMAIL_TO` одним письмом-дайджестом уходит админу (`send_summary_email` в mailer); пустой адрес — только файл.
   - Ошибки файла/SMTP попадают в `stats["errors"]`, цикл не падает; без новых дел ни файла, ни письма.
7. **Тесты**: `tests/test_matching.py`, `tests/test_monitor.py` (in-memory SQLite, моки KAD/SMTP), `tests/test_scheduler.py`, `tests/test_main.py` (TestClient), `tests/test_summary.py`.
