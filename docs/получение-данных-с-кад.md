# Получение данных с kad.arbitr.ru

Краткое описание того, как проект забирает дела из картотеки арбитражных дел (КАД)
и почему это сделано именно так.

## Суть в одном абзаце

Публичного API у КАД нет, поэтому используем внутренний эндпоинт сайта
`POST /Kad/SearchInstances`, но обращаемся к нему **из живой браузерной сессии
Playwright**, а не из HTTP-клиента: сайт защищён DDoS-Guard и собственной
проверкой **pravocaptcha** (WASM-модуль), без которой API отвечает `451
Доступ заблокирован`. Ответ приходит не JSON, а **HTML-фрагментом таблицы**,
который разбирает `parser.py`.

```
Playwright (headed Chromium или Xvfb) → bootstrap pravocaptcha (wasm.js -> кука wasm)
    → fetch('/Kad/SearchInstances', тело как у фронтенда)
    → HTML-фрагмент таблицы → parser.parse_response() → модели Case/Party
```

## Почему обычный HTTP-клиент не работает

Проверено экспериментально (по шагам, на реальном сайте):

| Подход | Результат |
|---|---|
| `httpx` + cookies из файла | 403/451 — нет куки `wasm` и не браузерный TLS |
| Playwright `context.request.post` | 451 — куку `wasm` никто не ставит |
| `fetch()` из страницы без pravocaptcha | 451 — анти-бот ждёт результат проверки |
| headless-Chromium + bootstrap pravocaptcha | WASM падает (`RuntimeError: unreachable`), кука не ставится → 451 |
| **headed-Chromium (или Xvfb) + bootstrap pravocaptcha** | **200, HTML с делами** ✅ |

Вывод: нужен именно «человеческий» браузер с дисплеем и прохождение WASM-проверки.
Схема «собрать cookies в браузере один раз и дальше слать их через httpx»
оказалась нерабочей — от неё отказались (модуль `cookie_fetcher.py` удалён).

## Как это устроено в коде

`app/services/kad/client.py`:

1. `_BrowserSession` — поднимает Chromium в headed-режиме с настройками,
   максимально похожими на обычного пользователя:
   `--disable-blink-features=AutomationControlled`, `locale=ru-RU`,
   `timezone_id=Asia/Yekaterinburg`, viewport 1600×900, светлая тема;
   открывает `kad.arbitr.ru`.
2. `_BOOTSTRAP_JS` — в живой странице выполняет цепочку pravocaptcha:
   `wasm.js → window.wasm.default(wasm_bg.wasm)` (модуль сам ставит куку `wasm`
   и вызывает `onwasm`), затем фингерпринт `fp.js → fp.default → fp.get()`;
   ждёт появления куки `wasm` (до 20 секунд).
3. `_PlaywrightWorker` — держит сессию в отдельном потоке (ограничение
   `sync_playwright`) и переиспользует её между запросами; `search()` — async
   обёртка над этим потоком.
4. Запрос отправляется `fetch()` из самой страницы с телом и заголовками как
   у фронтенда КАД (`Content-Type: application/json`, `x-date-format: iso`,
   `X-Requested-With: XMLHttpRequest`).

### Формат запроса (снят из браузера, HAR)

```json
{
  "Page": 1, "Count": 25,
  "Courts": ["EKATERINBURG"],
  "DateFrom": "2026-09-21T00:00:00",
  "DateTo": "2026-09-24T23:59:59",
  "Sides": [], "Judges": [], "CaseNumbers": [],
  "WithVKSInstances": false
}
```

Поля и их значения (снято из `returnRequestInfo` в `kad.*.js`):

| Поле | Смысл | Значения |
|---|---|---|
| `Page`, `Count` | пагинация | страница, размер (25) |
| `CaseType` | тип дела | `G` гражданские, `A` административные, `B` банкротные |
| `Courts` | суды | коды из `app/services/kad/courts.py`, напр. `EKATERINBURG` |
| `DateFrom`/`DateTo` | период | `YYYY-MM-DDTHH:MM:SS` или `null` |
| `Sides` | участники | `{Name, Type, ExactMatch}` |
| `Judges` | судьи | `{JudgeId, Type: -1}` |
| `CaseNumbers` | номера дел | список строк |
| `WithVKSInstances` | ВКС | `true`/`false` |

Роли участника (`Sides[].Type`, значения переключателя на сайте):
`-1` любой, `0` истец, `1` **ответчик**, `2` третье лицо, `3` иное лицо.
В коде удобно собирать участника через `client.side(name, role="ответчик")`.
Заголовок `RecaptchaToken` фронтенд добавляет, если проверка его вернула, но
на практике запрос проходит и без него — критична именно кука `wasm`.

### Формат ответа

`content-type: text/html` — фрагмент таблицы: по строке на дело
(`<a class="num_case" href=".../Card/{guid}">`), тип дела задаётся классом блока
даты (`civil` → Г, `administrative` → А, `bankruptcy` → Б), суд — `div[title]`,
судья — `div.judge` (часто отсутствует у свежих дел), стороны —
`span.js-rollover` в ячейках `td.plaintiff` / `td.respondent` (имя в `<strong>`,
ИНН и адрес — ниже; сторон может быть несколько).

Разбор — `app/services/kad/parser.py`: `parse_search_page()` принимает HTML-строку
(или JSON) и отдаёт `SearchPage` — список `Case` плюс пагинацию
(`page`, `page_size`, `total`, `pages`, сырой HTML для диагностики). Значения
`total`/`pages` КАД кладёт в скрытые `input`'ы ответа (`documentsTotalCount`,
`documentsPagesCount`).

## Пагинация и устойчивость

- `search_page(...)` — одна страница результатов; `iter_cases(...)` — асинхронный
  генератор по всем страницам с паузой `PAUSE_BETWEEN_REQUESTS_S` между ними
  (и ограничением `max_pages`, если нужно).
- Ретраи: `_post(...)` до 3 попыток с экспоненциальным бэкоффом — повторяем при
  обрыве сессии, 403/451 и неожиданных статусах; при 451 сайту даём «остыть».
- Watchdog: сессия проверяется перед каждым запросом; если страница/браузер
  умерли — поднимается новая сессия с повторным bootstrap pravocaptcha, а запрос
  повторяется. Это делает долгоживущий сервис (монитор) самовосстанавливающимся.

## Запуск

Локально (нужен дисплей):

```bash
uv run python scripts/kad_smoke.py             # поиск + разбор + краткий отчёт
uv run python scripts/kad_smoke.py --dump      # + сохранить сырой HTML в /tmp/kad_last.html
```

В контейнере с виртуальным дисплеем (Xvfb):

```bash
docker compose up -d app                              # Xvfb :99 стартует вместе с app
docker compose exec app python scripts/kad_smoke.py
docker compose exec app python scripts/kad_smoke.py --dump
```

Важно: `xvfb-run` внутри контейнера зависает (сигнальный протокол USR1 не
доходит до `wait`), поэтому в `Dockerfile` Xvfb запускается вручную:

```bash
Xvfb :99 -screen 0 1600x900x24 -nolisten tcp -noreset >/app/data/xvfb.log 2>&1 &
```

## Ограничения и риски

- **Только headed / Xvfb**: в headless API отвечает 451 (настройка
  `kad_browser_headless=True` — лишь для отладки, с предупреждением в логах).
- **Лимиты частоты**: при агрессивном опросе DDoS-Guard блокирует IP и API
  отдаёт 451 на любой запрос. Опрос — с интервалами, без параллельных запросов.
- **Хрупкость**: WASM-проверка и разметка страницы могут измениться на стороне
  КАД; ломается — смотрим `scripts/kad_smoke.py --dump` и правки в `parser.py`.
- **Правовой аспект**: условия использования сайта ограничивают
  автоматизированный доступ — учитывать при эксплуатации.
